## 一、判定基准：飞腾派 V3 的真实能力边界

先把"能不能跑"这件事锚定在硬指标上，后面的分级全部由这张表推导。

| 维度 | 实测/规格 | 对项目筛查的含义 |
|---|---|---|
| CPU | 2×FTC664@1.8GHz（乱序，A72 级）+ 2×FTC310@1.5GHz（顺序，A55 级），ARMv8-A aarch64 | 通用 Linux 软件能编能跑；**重 CPU 的 SLAM/仿真只能小规模**；线程数开 4 反而更慢（大核小核混跑） |
| 内存 | DDR4 2G/4G/8G 三档，本项目为 4G（可用约 3.7 GiB） | 排除所有 7B 以上模型、 Isaac/Genesis 级仿真、多传感器大场景建图 |
| 加速器 | **无 NPU、无 GPU**（E2000Q 只有显示控制器 DC）；AI 算力只能靠 miniPCIe 扩展卡 | 视觉推理走 CPU（ncnn/MNN/Tengine）；rviz2 只能软件渲染，**必须远程可视化** |
| 存储 | microSD（默认）或 eMMC，二者不共存 | rosbag / 数据集写入是瓶颈，**建议 USB3 外挂 SSD** |
| 摄像头输入 | 规格书未列 MIPI CSI，只有 HDMI 输出 | 视觉输入**只能 USB UVC**；CSI 方案（Jetson/树莓派常见）不可移植 |
| 板载传感器 | 规格书未列 IMU | 所有 VIO/LIO 项目都要**外接 IMU 或由 STM32/从核提供**，这是最大的隐性成本 |
| 总线 | 2×GbE、4×USB3.0（1 路可改 OTG）、1×CAN FD、2×UART、2+2×I2C、2×SPI、1×I2S、40PIN（仅 1 路 PWM）、1×miniPCIe（PCIe x1 + USB + UART3 + SIM） | **CAN FD 是稀缺优势**（直连伺服/关节）；PWM 只有 1 路，舵机必须走 I2C 扩展或下放 MCU |
| 系统 | 原厂 PhytiumPI OS（Debian 12，内核 6.6.63）；另支持 Ubuntu、Armbian、OpenWRT、OpenHarmony、OpenKylin、Deepin、SylixOS、RT-Thread | **Debian 12 没有 ROS 2 官方二进制包**，这是第一个坑 |
| 异构能力 | OpenAMP + remoteproc 把 CPU3 交给 FreeRTOS，RPMsg 双向通信**本项目已打通** | 这是飞腾派相对树莓派/Jetson 的**唯一差异化卖点**，应作为主线而非附属 |

### 分级定义

| 级别 | 含义 | 典型工作量 |
|---|---|---|
| **A** | 可直接复现：aarch64 有包或源码可编，纯 CPU，≤4 GB，无特殊外设 | 1–3 天 |
| **B** | 需适配后能跑：改构建/裁剪模型/补驱动/加外设 | 1–3 周 |
| **C** | 只能当上位机或代码参考：本体需 GPU、专用传感器或另一颗芯片 | 不建议作为主线 |
| **D** | 不适用：绑定 RISC-V/FPGA/x86 或专用 NPU，无移植价值 | 直接放弃 |

> 说明：标「已实证」的为本项目实测或社区公开实证；其余为基于架构、依赖链与官方 BSP 支持情况的工程判断，落地前仍需实测。

## 二、结论速览

| 分级 | 条目数 | 说明 |
|---|---|---|
| A | 18 | 视觉推理、嵌入式组件、物联网中间件、教学 SLAM |
| B | 16 | ROS 生态、激光 SLAM、RT-Thread/hvisor、开源硬件上位机 |
| C | 14 | 遥操作、CUDA 感知、本体为 STM32 的创客项目 |
| D | 约 170 | 大模型/VLA、GPU 仿真、RISC-V 与 FPGA、专用 NPU 工具链 |

**最值得投入的五件事**（按性价比排序）：

1. **ARM 原生视觉检测流水线**（ncnn + V4L2 + OpenCV）——已有实测基线，直接扩品类。
2. **AMP 异构：Linux 视觉 + CPU3 FreeRTOS 硬实时**——飞腾派独有，竞品做不了。
3. **RT-Thread 替代 FreeRTOS 跑从核**——官方 BSP 已适配飞腾派，驱动齐全，省掉大量裸机驱动工作。
4. **ROS 2 边缘节点 + CAN FD 关节控制**——"国产化机器人控制器"这个生态位目前是空的。
5. **hvisor 分区隔离**——官方已支持飞腾派，可做可信/混合关键级方案，适合冲奖项与论文。

## 三、机器人操作系统与运行时

> 仓库本身没有单列 ROS，但它是绝大多数机器人项目的前置条件，因此单列。飞腾派上 ROS 2 的可行路径已由社区项目《基于飞腾派多核异构的 2D 激光 SLAM 小车》实证：**Ubuntu 22.04 镜像 + ROS 2 Humble + Cartographer**；Debian 12 下则需 Docker 或源码编译，不建议。

| 项目 | 用途 | 关键依赖 | 分级 | 在飞腾派 V3 上的判断 |
|---|---|---|---|---|
| **RT-Thread** | 国产 RTOS，组件生态完整 | `bsp/phytium` + Phytium-Standalone-SDK，aarch64/aarch32，SMP | **A（已实证）** | 官方 BSP 明确支持 PHYTIUMPI（TARGET_PE2204），UART/GPIO/XMAC/SDMMC/PWM/CAN/I2C/SPI/QSPI/DC/USB3(XHCI) 全有驱动；官方还提供 CherryUSB、LVGL 应用与"固化到 SD 卡"的文档。**建议直接用它替换当前 FreeRTOS 从核方案**。唯一坑：RT-Thread 读写 SD 会影响固件分区，需按官方文档做固化 |
| **AimRT** | 现代 C++ 机器人运行时，兼容 ROS 2/HTTP/gRPC，自带插件与协程调度 | C++17、CMake、可选 ROS 2/zenoh 插件 | **A** | 纯 C++ 无 CUDA 依赖，aarch64 可源码编译；相比 ROS 2 在 ARM 上更轻，适合做"去掉 DDS 开销"的实时链路。适合替换当前自研协议层，但要评估与 RPMsg 的契合度 |
| **hvisor** | Rust 写的 Type-1 轻量 Hypervisor，Zone0/ZoneU/ZoneR 分区隔离 | Rust 工具链、U-Boot 引导、分区配置文件、`hvisor-tool` | **B（官方已支持）** | v0.2 起官方支持飞腾派（腾珑 E2000），已在飞腾派上跑通多 VM、GICv3、virtio console/block/net；OS 大赛有队伍做到 Linux + RT-Thread + seL4 三区共存。**这是 OpenAMP 的"升级替代"**：隔离性更强，但启动链更复杂，需先解决 U-Boot 环境变量 CRC 损坏问题 |
| **OpenHarmony** | 分布式全场景 OS | 飞腾官方 `OpenHarmony(E2000/PhytiumPi)` 仓库，标准系统，内核 5.10，需 Ubuntu 18/20 编译环境 | **B** | 厂商有官方移植仓库，能跑；但编译产物数十 GB、工具链重、与现有 Debian 生态割裂，**只建议做"国产化 OS 演示"分支，不要作为主线** |
| openvela / TencentOS Tiny / AliOS Things / Huawei LiteOS | MCU 级 IoT RTOS | Cortex-M 为主 | **D（本板）/ C（协处理器）** | 定位是 MCU，跑在 A 核 Linux 上无意义；若 STM32 侧要换 RTOS 可评估，但与飞腾派无直接关系 |
| 星绽 Asterinas / DragonOS / rCore-Tutorial / RustSBI | 操作系统教学与研究内核 | x86_64 为主；RustSBI 为 RISC-V 专用 | **D** | 架构不匹配（RustSBI 绑定 RISC-V SBI，aarch64 无对应物）。若想做内核方向，改 hvisor 更有价值 |
| 香山 / 果壳 NutShell / tinyriscv / 蜂鸟 E203 / 玄铁 C910 | RISC-V 处理器与 SoC 设计 | Verilog/Chisel、FPGA、EDA 工具 | **D** | 属于芯片设计，需 FPGA 板；与飞腾派（ARMv8）无交集。可作《计算机体系结构》课程素材，不能作为板卡项目 |

## 四、SLAM、感知与状态估计

**这一类的最大约束不是算力，而是传感器**：板子没有 CSI、没有 IMU。所有 VIO/LIO 项目都必须先解决 IMU 来源（USB IMU 模块，或 STM32 采样后经 UART/RPMsg 上传并做时间同步）。

| 项目 | 用途 | 关键依赖 | 分级 | 在飞腾派 V3 上的判断 |
|---|---|---|---|---|
| **视觉 SLAM 十四讲（slambook2）** | SLAM 教学与代码实践 | OpenCV 4、Eigen3、Ceres、g2o、Pangolin（OpenGL） | **A** | 依赖链完整可编；Pangolin 在无 GPU 下靠 llvmpipe 软件渲染，1080p 会卡，**建议只跑算法章节、关掉可视化**。是最合适的团队入门项目 |
| **VINS-Mono / VINS-Fusion** | 单目/双目 + IMU 视觉惯性里程计 | Ceres、OpenCV、ROS 1（Mono）/ ROS 1&2（Fusion）、IMU | **B** | CPU-only 可行，640×480 单目预计 10–20 Hz；**必须先接 IMU 并做硬同步**，否则精度无从谈起。Fusion 支持双目，但 USB 双目相机带宽与同步是新的坑 |
| **FAST_LIO** | 紧耦合 LiDAR-惯性里程计，工程界事实标准 | PCL、Eigen、livox_ros_driver2/标准 LiDAR 驱动、IMU | **B+** | 4 核可跑，建议 16 线 + 关闭 PCD 保存，目标 10 Hz；内存占用可控。**是激光方案里最值得先试的一个** |
| **LIO-SAM** | 平滑建图 + 回环 | GTSAM、PCL、9 轴 IMU、ROS | **B-** | GTSAM 因子图在 4 核上偏重，长距离回环会掉帧；建议降线数、缩短建图范围，或改用 FAST_LIO |
| **FAST-LIVO2** | LiDAR-惯性-视觉紧耦合 | PCL、Vikit、OpenCV、LiDAR+相机+IMU 三传感器同步 | **C+** | 峰值内存与 CPU 都高，4 GB 版风险大；三传感器硬同步在 USB 相机上很难做 |
| **R3LIVE** | RGB 彩色点云建图 | PCL、OpenCV、LiDAR+相机+IMU | **C** | 同上，且代码年代较早，依赖冲突多 |
| **point_lio_unilidar** | 宇树 L1 4D LiDAR 的 SLAM 适配 | 宇树 L1 硬件 + Point-LIO | **C** | 绑定特定雷达，除非采购同款，否则只作参考 |
| **小觅 MYNT-EYE-S-SDK** | 双目相机 SDK | 特定相机、老旧 SDK | **C** | 产品线已边缘化，aarch64 支持不明确；新项目建议直接用标准 UVC 双目 |

> **实证参考（不在仓库内，但极有价值）**：社区项目 `wang-ruifan/2DSLAMCar-BasedOn-Phytiumpi` 已在飞腾派上跑通 ROS 2 Humble + Cartographer + FreeRTOS 从核，并记录了 GPIO 中断注册、PWM 通道号错位等驱动坑。**结论：2D 激光 SLAM 是飞腾派上的 A 级路线，3D 多传感器融合只能算 B/C。**

## 五、仿真、数据集与遥操作

**结论先行：仿真不要在板上做。** 板上只做三件事：策略部署（ONNX/ONNX Runtime CPU）、真机数据采集、遥操作从端。训练与仿真放 PC/服务器。

| 项目 | 用途 | 关键依赖 | 分级 | 在飞腾派 V3 上的判断 |
|---|---|---|---|---|
| **unitree_mujoco** | MuJoCo 中的宇树机器人仿真，集成 unitree_sdk2 | MuJoCo 3.x（aarch64 wheel 可用）、CycloneDDS、unitree_sdk2 | **B** | 纯 CPU 可跑，小场景（单机、少量接触）能实时；复杂场景会掉到 0.5× 以下。**适合做"无硬件联调"**：先用仿真验证 DDS 话题与状态机，再上真机 |
| **unitree_sdk2 / sdk2_python / unitree_ros2** | 宇树机器人 DDS 通信与控制 | CycloneDDS、C++17/Python、网卡配置 | **B+** | aarch64 可编；飞腾派双千兆网口正好一路接机器人、一路接上位机。**若做四足/人形二次开发，这是最实用的入口** |
| **Genesis** | 通用物理仿真引擎，主打 GPU 并行 | CUDA GPU（CPU 后端性能差一个量级） | **C** | 无 GPU 时速度优势消失，只适合跑极小场景做算法验证；不推荐 |
| **ManiSkill / SAPIEN** | 操作技能仿真与基准 | Vulkan GPU、SAPIEN | **D** | 需要 Vulkan 渲染，E2000Q 无 GPU，直接放弃 |
| **RoboTwin** | 双臂数据生成与基准 | GPU + 大规模渲染 | **D** | 同上 |
| **Isaac Lab / unitree_sim_isaaclab / unitree_rl_gym / humanoid-gym / Dreamwaq** | 强化学习训练框架 | NVIDIA GPU、Isaac Gym/Lab | **D（训练）/ B（部署）** | 训练必须 GPU；但**策略导出 ONNX 后在板端 CPU 跑 200–1000 Hz 完全可行**，这条"PC 训练、板上部署"的路径建议写进方案 |
| **AgiBot-World / EmbodiedGen** | 大规模操控平台 / 生成式 3D 资产 | GPU、大存储 | **D** | 数据与资产生成侧工具，与板端无关 |
| **Open-TeleVision / xr_teleoperate / OpenWBT** | VR 遥操作 | VR 头显、GPU 视频编码、低延迟网络 | **C** | 主控在 PC/头显侧；飞腾派只能做**从端关节控制 + 相机采集**，且 USB 相机编码延迟需实测 |
| **XLeRobot** | 约 660 美元的开源双臂移动家用机器人，兼容 LeRobot | USB 相机、Feetech 舵机总线、12V 电源 | **B** | 电源规格（12V）与本板一致，aarch64 上 PyTorch CPU 可跑 ACT 类小策略推理，**训练不行**。适合做"低成本双臂 + 国产算力"的演示组合 |
| **unitree_IL_lerobot** | 基于 LeRobot 的模仿学习工具链 | PyTorch、GPU 训练 | **C** | 训练侧工具，板上仅能推理 |

## 六、嵌入式软件组件与中间件

**这是最容易出成果、也最被低估的一类**：纯 C、无依赖、可直接编进从核 FreeRTOS 或 STM32，与飞腾派"一芯两系统"的定位天然契合。

| 项目 | 用途 | 关键依赖 | 分级 | 在飞腾派 V3 上的判断 |
|---|---|---|---|---|
| **EasyLogger** | 超轻量日志（ROM<1.6K，RAM<0.3K） | 纯 C，需移植输出后端 | **A** | 从核/STM32 直接用；也可在 Linux 侧做统一日志格式，方便三端对齐 |

| **SFUD** | SPI/QSPI Flash 通用驱动（JEDEC SFDP） | 纯 C，SPI 底层 | **A** | 板上有 QSPI 烧录位与 SPI 接口，RT-Thread BSP 已含 QSPI；可做参数分区 |
| **letter-shell** | 嵌入式命令行，支持命令导出与补全 | 纯 C，需串口/字符输入 | **A** | 从核调试利器；配合 RPMsg 可让 Linux 侧远程下发命令，比反复烧固件高效得多 |
| **MultiButton / MultiTimer** | 事件驱动按键 + 软件定时器 | 纯 C | **A** | 从核侧做超时/看门狗逻辑的基础件，可直接补上"从核无看门狗"这个缺口 |

| **mqttclient** | 高性能 MQTT 客户端，支持 Linux 与 RTOS | 纯 C | **A** | 三端（Linux/从核/STM32）可用同一套 MQTT 语义上报 |
| **Tengine** | 嵌入式 AI 推理引擎，ARM 有汇编优化 | C/C++，CMake | **B+** | aarch64 可编，可作为 ncnn 的对照后端；算子覆盖不如 ncnn 全，需逐模型验证 |

| **AWTK / MiniGUI / GuiLite** | 嵌入式 GUI | Framebuffer/DRM、C/C++ | **B** | HDMI 1080p 输出可跑，但**无 GPU 全靠软件绘制**，动画要克制；AWTK 对 aarch64 支持最完整，适合做本地 HMI（工位看板） |

## 七、开源硬件与创客项目

飞腾派在这些项目里的角色统一是**上位机/大脑**，不是本体控制器。判断标准：本体是否用 STM32/ESP32 + 该项目是否只暴露串口/网络协议。

| 项目 | 用途 | 关键依赖 | 分级 | 在飞腾派 V3 上的判断 |
|---|---|---|---|---|
| **树莓派目标识别与追踪（automaticdai/rpi-object-detection）** | 树莓派 + USB 相机 + ncnn 的实时检测追踪 | OpenCV、ncnn、V4L2 | **A（已实证同构）** | **与本项目技术栈几乎完全一致**（同为 aarch64 Linux + V4L2 + ncnn），改设备节点与线程数即可跑。建议作为"视觉流水线"的起步模板 |
| **Jetson 实时检测追踪（nvidia-jetson-object-detection）** | Jetson + PyTorch 的 GPU 版 | CUDA、PyTorch、TensorRT | **C** | CUDA 路径不可用；但**工程结构（取图→预处理→推理→跟踪→输出）可复用**，把后端换成 ncnn 即可 |

## 十一、推荐的五个开发方向

按"能出成果 + 有差异化 + 风险可控"排序，每条给出起步路径与验收指标。

### 方向 1：ARM 原生视觉质检流水线（最稳，直接复用现有基线）

- **技术栈**：V4L2（USB UVC）→ OpenCV 预处理 → ncnn（YOLOX/自研）→ 结果判定 → 协议上行
- **参考项目**：`rpi-object-detection`（同构迁移）、`YOLOX`、`ncnn`、`MNN`（对照）
- **已验证约束**：320 输入 / 2 线程 / 端到端 250 ms 预算内有约 127 ms 余量
- **可扩展点**：多模型级联（检测 + 分类）、量化（int8）对比、MNN 与 ncnn 的 A/B
- **验收**：单帧 320 输入 P50 ≤ 130 ms；连续 8 h 无内存增长；断电重启自恢复
- **风险**：USB 相机带宽与曝光抖动；SD 卡写入瓶颈（日志与图像落盘要限流）

### 方向 2：AMP 异构 —— Linux 视觉 + 从核硬实时（差异化最强）

- **现状**：RPMsg 双向已打通，但引导不持久、从核无看门狗
- **升级路径**：把从核从裸 FreeRTOS 换成 **RT-Thread**（官方 BSP 已适配飞腾派，UART/GPIO/CAN/PWM/SPI 全有驱动），并引入 `EasyLogger` + `FlashDB` + `letter-shell` + `MultiTimer`
- **价值**：把"Linux 非实时 + RTOS 实时"的分工做成产品级能力：Linux 负责视觉与网络，从核负责 ≤1 ms 的 IO 与安全联锁
- **验收**：上电自动拉起从核（解决当前最大翻车点）；从核心跳丢失 100 ms 内 Linux 侧可感知并锁存故障；从核参数可掉电保存
- **风险**：RT-Thread 在飞腾派上读写 SD 会影响固件分区，必须按官方"固化"文档操作；建议先在 eMMC/USB 上验证

### 方向 3：ROS 2 边缘节点 + CAN FD 关节控制（生态位空白）

- **技术栈**：Ubuntu 22.04 镜像 + ROS 2 Humble（ros-base，不装 desktop）+ `ros2_canopen` 或自研 CAN 节点 + `unitree_sdk2` 风格 DDS
- **为什么可行**：社区已在飞腾派跑通 ROS 2 + Cartographer；板载 **CAN FD** 是树莓派没有的，直连伺服驱动器天然合适
- **建议架构**：板子只跑 `ros-base` + 自研节点，**rviz2/Foxglove 放 PC 远程看**（无 GPU，本地 rviz 会拖垮整机）
- **验收**：1 kHz CAN 周期抖动 P99 < 200 µs；ROS 2 节点 CPU 占用 < 40%；远程 Foxglove 延迟 < 150 ms
- **风险**：Debian 12 与 ROS 2 版本错配，必须走 Ubuntu 镜像或 Docker；DDS 在双网口下的组播配置是常见坑

### 方向 4：本地 HMI 与人机交互（低成本高观感）

- **技术栈**：AWTK（aarch64 支持最完整）或 LVGL + Framebuffer，配合 `libhv` 提供 Web 兜底
- **价值**：HDMI 1080p 直出，工位看板/参数设置不依赖 PC；软件渲染下动画克制即可
- **验收**：1080p 静态界面刷新 ≥ 20 fps；触摸/键鼠响应 < 100 ms；与推理线程互不抢占（绑核）
- **风险**：无 GPU，全屏重绘代价高；建议局部刷新 + 双缓冲

### 方向 5：hvisor 分区隔离（研究/竞赛向）

- **价值**：官方已支持飞腾派，可做"Linux + RT-Thread + 可选 seL4"三区隔离，是 OpenAMP 的升级形态；适合论文、OS 竞赛、可信执行叙事
- **起步路径**：先在 QEMU 跑通 hvisor 配置 → 迁移到飞腾派（官方 platform 目录已有板级配置）→ 打通 zone0 Linux 与 zoneU RT-Thread 的 virtio 通道
- **验收**：双区同时启动；virtio console/block 可用；分区故障不扩散
- **风险**：引导链比 OpenAMP 更复杂（hvisor → zone0 Linux → zoneU），且当前 U-Boot 环境变量 CRC 已损坏，需先修复再谈持久化

## 十二、明确不建议在飞腾派 V3 上做的事

| 不做 | 原因 | 替代方案 |
|---|---|---|
| 端侧跑 VLA / 7B+ 大模型 | 无 NPU、4 GB 内存、无 GPU | 远端 API 推理 + 板端执行动作；或只做"小模型感知 + 规则决策" |
| Isaac Lab / Genesis / ManiSkill 训练与仿真 | 需 NVIDIA GPU / Vulkan | PC 训练 → ONNX → 板端 CPU 推理（200–1000 Hz 可行） |
| 3D 多传感器紧耦合 SLAM（FAST-LIVO2/R3LIVE） | CPU/内存峰值超标，三传感器硬同步难 | 2D 激光 SLAM（Cartographer，已实证）或 FAST_LIO 单雷达方案 |
| CSI 摄像头方案 | 板子无 MIPI CSI | 全部改 USB UVC，注意带宽与曝光 |
| 用 40PIN 直接驱动多路舵机 | 仅 1 路 PWM，且 IO 不能直驱感性负载 | I2C 舵机驱动板（PCA9685）或下放 STM32 |
| 在板上做实时可视化 | 无 GPU，rviz2 软件渲染会拖垮整机 | rviz2/Foxglove 放 PC，板端 headless |
| 把 rosbag/数据集写 SD 卡 | SD 卡随机写慢且伤寿命 | USB3 SSD 外挂 |

## 十三、落地检查清单

- [ ] 确定 OS 基线：继续 Debian 12（放弃 ROS 2 官方包）还是切 Ubuntu 22.04（拿 ROS 2 Humble）
- [ ] 修复 U-Boot 环境变量 CRC，为 AMP/hvisor 持久化铺路
- [ ] 选定从核 OS：FreeRTOS（现状）vs RT-Thread（官方 BSP，驱动更全）
- [ ] 补 IMU（USB 或 STM32 上传）——所有 VIO/LIO 项目的前置
- [ ] 确认 USB 相机型号与 UVC 支持情况，实测 1080p/720p 带宽
- [ ] 准备 USB3 SSD，用于数据集与 rosbag
- [ ] 锁定 Phytium FreeRTOS SDK / RT-Thread BSP 的提交号，避免上游漂移
- [ ] 决定是否需要 miniPCIe AI 加速卡（当前算力余量充足，建议不加）
