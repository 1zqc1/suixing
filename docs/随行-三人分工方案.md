# 随行项目三人分工方案

**主开发与整机集成放在队长电脑。队友 A 负责感知与风险算法，队友 B 负责交互与独立验收。**

## 1. 成员分工表

| 成员与设备 | 主责 | 第一轮交付物 | 验收与备份 |
|---|---|---|---|
| **队长（主开发机）** · Core Ultra 9 285H，约 32 GB 内存，RTX 5060 8 GB | **设备接入、整机集成与安全闭环（M1、M4–M6）**。负责飞腾派上的 D6、双目、轮速和手柄接入，统一 ROS 2 话题、时间戳、TF 和诊断。负责 CPU3 FreeRTOS、OpenAMP/RPMsg、STM32 台架和正式固件发布，确认电源、电机、驱动与急停接口。集中保存原始录包，安排长录包及多传感器并发回归 | 最小 `rosbag2`、同一时段导出的图像与 JSONL、模拟车况 JSON、接口约定、RPMsg 业务样例、STM32 无人台架记录 | B 按验收脚本独立复测，A 协助定位传感和风险接口问题。STM32 开发及台架操作由队长负责 |
| **队友 A（8940HX 电脑）** · Ryzen 9 8940HX，16 核 32 线程，16 GB 内存，RTX 5060 8 GB，1 TB SSD | **感知与风险算法（M2、M3）**。先完成双目视差、几何风险与 TTC，再做 YOLOv8n 微调、ONNX 导出和语义关联。短样本分批处理，长录包由 A 提供脚本和指标、队长安排执行 | 几何风险节点及复现脚本，含有障碍、无障碍、数据断流三个短用例。语义阶段再交付固定数据划分、带版本和哈希的 ONNX、同场景开关对照 | 队长在 22.04 上重编并对接飞腾派，B 按固定数据和预期结果复测 |
| **队友 B（13620H 电脑）** · Core i7-13620H，10 核 16 线程，RTX 4050 6 GB。照片显示两条 8 GB 内存，按约 16 GB 安排 | **交互与测试证据（M7–M9）**。负责 ESP32-S3 离线语音和震动提示、Android 只读车况与地图、回归和故障记录。实物阶段跟踪 V4 支架尺寸、装配清单与无动力检查 | 可运行的只读 Debug APK、ESP-SR 样例固件与真机音频验证记录、可复跑的回归脚本、故障和复测记录。硬件未到位时先用模拟状态验证接口 | 队长审核交互接口是否影响安全链，A 复核算法对照和回归数据 |

## 2. 三台电脑怎么用

| 环境 | 用途 |
|---|---|
| **三人共有的 `phytium-dev` 克隆 · Ubuntu 24.04** | 通用 Linux 开发和轻量回归。A 使用导出的图像、JSONL 做分批 OpenCV 处理，B 用模拟车况和短样本跑回归。两位队友运行克隆时可先按 4 GiB 来宾内存安排 |
| **队长的 `Suixing-Jammy` · Ubuntu 22.04.5 + ROS 2 Humble** | 正式构建 Humble 节点、RViz2 验证、AArch64 交叉编译及发版前复测。由此统一执行完整 `rosbag2` 回放和雷达、双目并发验收 |
| **三台 Windows 宿主机** | A 用 RTX 5060 训练和导出。用小样本、小批量起跑，数据按批从 SSD 读取，并将训练与 VMware、批量预处理错峰。B 在 Windows 做 ESP-SR 和 Android，优先用手机真机调试，按任务切换 Android Studio、ESP-IDF 和 VMware |

**跨机交接以源码、模型和数据为主。** 来自 24.04 的改动提交到 Git 后，由队长在 22.04 上构建同一个提交，交 B 复跑验收用例。录包和模型通过共享目录交付，随附版本、校验值和复现说明。

## 3. 联调顺序与通过条件

| 阶段 | 三人各自推进 | 通过条件 |
|---|---|---|
| **① 接口与样本 · 首个 48 小时目标** | 队长提供短录包、同一时段的图像和 JSONL、模拟车况 JSON，并确定话题名、坐标系、采样时间、序号、质量标志与有效期。A 先交三个几何短用例，B 用模拟车况做只读状态页及回归脚本，同时清点阻塞台架的缺件 | A、B 能独立读入样本，队长用一条正常和一条过期风险摘要验证 CPU3 接收行为。实物未到位时使用同接口的合成样例 |
| **② 几何链与安全台架** | A 交付几何风险输出。队长接通 `RiskSummary` → CPU3 → STM32，在无人台架测过期、失联、急停与制动回读。B 用同一录包独立复测并整理证据 | 关闭 YOLO 后，几何链仍能识别危险。按总纲通过 P0 安全闭环后，再进入有人动态测试 |
| **③ 语义、交互与演示** | A 交付同一场景的 YOLO 开关对照。B 接入语音、震动、手机只读状态和断网回归。队长提交可复现的整机版本并组织彩排 | App 断网、语音异常或语义掉线时，本地安全链仍按预期运行。Hailo 卡型和工具包确认后，由 A 编译模型、队长上板验收、B 记录对照结果 |

每次交接附上 **Git 提交号、数据或模型版本、运行命令、预期与实测结果**。比赛材料按同一分工整理，由队长提供整机和板端证据，A 提供算法对照，B 汇总演示脚本、复现步骤与测试记录。

依据《随行-双赛冲击国一总纲 V1》的模块边界和阶段门禁，以及团队电脑配置和主开发机的 Ubuntu 22.04 验收结果。
